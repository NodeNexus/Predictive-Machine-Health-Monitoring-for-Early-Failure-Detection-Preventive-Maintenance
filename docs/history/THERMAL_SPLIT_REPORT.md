# Thermal Dataset Split Report

Companion to `docs/history/THERMAL_DATASET_AUDIT.md`. This document covers **only** train/validation/test split preparation — no model was trained. Generated by `scripts/prepare_thermal_splits.py` (rerunnable, deterministic, seed=42). Manifests: `data/manifests/thermal_dataset1_split.json`, `data/manifests/thermal_dataset2_split.json`.

---

## 1–2. Dataset 1 methodology and group discovery

**Investigated, in order, per the task's preferred priority:**

1. **Explicit source/acquisition grouping** — none provided by the dataset itself.
2. **Metadata grouping** — investigated and **found**: every one of the 488 JPEGs carries a real embedded ASCII timestamp (`YYYY:MM:DD HH:MM:SS`, extracted by a plain regex over the raw file bytes — no FLIR radiometric parsing involved). Coverage: 488/488 (100%). This confirmed, for every class, that **filename order matches timestamp order exactly**, and each class is **one single continuous capture session on 2024-07-31** (sessions run back-to-back across classes: CNL 09:35→09:49, CML 09:49→10:06, CFL 10:06→10:16, HNL 10:55→11:11, HML 11:10→11:25, HFL 11:34→11:48 — the ~45 minute gap between CFL and HNL is a real break in the session, not measured further).
3. **Near-duplicate clustering** — attempted as a cross-check. A dHash (8×8 difference hash) was computed for every image, and Hamming distance measured between chronologically-consecutive frames within each class. **Result: no clean bimodal cutoff exists.** Distances form a smooth, continuous spectrum from 0 to 20+ (median 4–9 across classes) — consistent with the motor's thermal state evolving gradually through each session rather than the camera producing bursts of identical frames. Any fixed similarity threshold here would be an arbitrary judgment call, not a discovered structural fact.
4. **Filename/order-based grouping** — used as the **primary method**, justified by finding #2 above (real, confirmed acquisition timestamps, not an assumption about file naming).

**Chosen method:** chronological block split *per class*: earliest ~70% of that class's session → train, next ~15% → validation, last ~15% → test, with a 2-image buffer dropped at each of the two cut points (removed from all splits) to reduce boundary-adjacency risk.

**This alone was insufficient** — an independent post-split verification (all-pairs dHash, train vs. validation/test, and validation vs. test, threshold ≤2) found **28 residual near-duplicate cross-split pairs**, concentrated in the smallest class (CFL: 23 of 28). Investigation showed these were **not confined to the boundary** — e.g. a training image at chronological position 22 matched a validation image at position 36 in CFL — meaning visual similarity is not strictly monotonic with time distance in this data; a simple contiguous buffer cannot catch it. **A leak-repair pass was therefore added**: after the initial chronological assignment, every validation/test image is checked against all training images (and validation against all test images) in the same class; any near-duplicate (dHash ≤2) is demoted to *excluded* rather than kept. This is not a workaround for a methodology that doesn't fit the data — it is the correct safety net for data whose similarity structure has no clean threshold. **13 images were demoted** for Dataset 1 (result independently re-verified: 0 cross-split violations remain, checked below).

**Problem, not hidden:** **CFL's validation set has only 2 images.** CFL is both the smallest class (49 total) and the one whose session showed the most non-monotonic similarity recurrence, so it lost the largest fraction to leak-repair (9/49, 18%). A 2-image validation set cannot support a statistically reliable per-class validation estimate — any validation accuracy computed for CFL specifically should be treated as anecdotal, not a trustworthy metric, until more CFL data is collected or a different validation strategy (e.g. k-fold repeated across sessions, if more sessions become available) is used.

## 4–5. Dataset 2 methodology and class distribution

**Investigated:**

1. **Explicit/metadata grouping** — BMP has no EXIF container. OS file-modification timestamps were checked as a fallback and **found unreliable**: within several classes, mtime order did not match filename order at all, and gaps were irregular (tens of minutes) in a way inconsistent with the ~13–18s median gaps seen elsewhere — consistent with these being **artifacts of RAR-archive extraction order**, not real capture timestamps. They were explicitly **not used**.
2. **Near-duplicate clustering** — used as the **primary method** instead, since it was the only reliable signal available: dHash computed for every image, **all-pairs** Hamming distance within each class (feasible — each class has ≤42 images), connected components at threshold ≤2 define non-splittable groups. Groups assigned to train/validation/test via a seeded (seed=42) greedy algorithm that repeatedly assigns the next group to whichever split is furthest below its 70/15/15 target for that class.

**Severe, class-specific finding — not hidden:** four classes (**A10, A30, A&C10, A&C30**) each collapsed into **one giant connected component** (33–37 of their ~31–38 images, plus 1–2 singletons) at threshold ≤2. Visual inspection of a contact sheet confirms this is real: consecutive thumbnails in these four classes are visually almost indistinguishable, unlike other classes (Rotor-0, Fan, A50, A&B50, A&C&B30) which show clear visible variation across their samples. **A looser threshold would only make this worse** (it can only merge groups further, never split them) — this was verified by checking the same data at threshold ≤5 in an earlier exploratory pass, which showed even higher connectivity. This is a genuine property of how these four conditions were captured (steady-state, minimal visual change during the session), not an artifact of the grouping method or threshold choice.

**Consequence:** these four classes get **zero validation and zero-or-near-zero test images**:

| Split | Noload | Rotor-0 | Fan | A50 | A&B50 | A30 | A&C30 | A&C&B30 | A10 | A&C10 | A&C&B10 | Total |

| train | 17 | 21 | 20 | 27 | 23 | **37** | **37** | 35 | **34** | **31** | 28 | 310 |
| validation | 4 | 4 | 4 | 3 | 3 | **0** | **0** | 4 | **0** | **0** | 1 | 23 |
| test | 4 | 5 | 4 | 5 | 12 | **0** | **1** | 3 | **0** | **0** | 2 | 36 |

| **Total** | 25 | 30 | 28 | 35 | 38 | 37 | 38 | 42 | 34 | 31 | 31 | 369 |

**A10, A&C10 have literally zero held-out images of any kind.** A30 and A&C30 have zero validation and 0–1 test images. **No classifier evaluation can be trusted for these four classes under this split** — this is a dataset limitation (insufficient visual diversity in how those specific conditions were captured), not something a different split algorithm can fix without either accepting leakage or discarding most of the class.

## 9. Known limitations

- **Dataset 1's class semantics (H/C/F/M/N) meaning is still only confirmed for this task's purposes by the values you supplied in the prompt** (Healthy/Corroded Bearing × Full/Medium/No Load) — the previous audit found no local documentation confirming this; it is used here as given, not re-derived.
- **CFL validation set (2 images)** is too small for a trustworthy per-class validation metric.
- **A10 and A&C10 have zero held-out images**; A30 and A&C30 have effectively zero. Any reported accuracy on these four classes from this split should not be trusted.
- The dHash/threshold=2 near-duplicate definition is a **judgment call**, clearly documented as such — it is not a bimodal fact discovered in the data (Dataset 1 explicitly has no such clean cutoff; Dataset 2's separation into "one giant blob" vs. "several distinct groups" per class is much clearer, but the exact threshold value (2) is still a choice, verified not to be overly aggressive by checking that a looser threshold only makes things worse, not better).
- Dataset 1's 45-minute gap between the CFL and HNL sessions was noted but not further investigated (e.g. whether ambient conditions shifted during the break).
- No contact sheets were generated for the 40-image ground-truth subset of Dataset 2 (out of scope — those are segmentation masks, not classification data, per the prior audit).

## 10. Is this split ready for model training?

**Partially — with the class-specific caveats above made explicit rather than hidden.**

- Dataset 1: **ready** for a healthy-vs-fault (or 6-way) classifier, with the caveat that **CFL's validation metric will be statistically weak** (n=2) and should be interpreted cautiously; test (n=4) is also small for CFL specifically.
- Dataset 2: **ready** for the 7 classes with real validation/test representation (Noload, Rotor-0, Fan, A50, A&B50, A&C&B30, A&C&B10), but **not ready** for a trustworthy evaluation of A10, A30, A&C10, A&C30 — training on these classes is possible (310 train images span all 11 classes), but their held-out metrics cannot be trusted under this split. This should be resolved (more diverse captures, or an explicit documented exception) before any severity-classification claim is made using those four classes specifically.

Both manifests are internally leak-verified (zero exact or near-duplicate cross-split pairs, independently re-checked) and reproducible (fixed seed, deterministic construction, 88+15 automated tests passing).
